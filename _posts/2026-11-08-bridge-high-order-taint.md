## 논문을 고른 이유

최근 확인한 여러 보안 뉴스 중 IoT 관련 사고 뉴스를 접했었다. 논문 제목을 보고 IoT 관련 보안 논문인 것 같아 큰 고민 없이 바로 선정하고 읽어 보았다.

## 읽기 전에 던진 질문

### Q1. 이 논문은 어떤 문제를 풀려고 할까?

- 읽기 전: IoT 펌웨어 관련 새로운 취약점이 발견됐고 이에 관한 논문 같아 보였다.
- 읽은 후: 기존 분석 방식은 IoT 펌웨어에서 주로 일차 취약점을 분석했는데, 이 논문은 high-order 취약점까지 분석할 수 있는 Bridge를 제시한다.

### Q2. 그 문제는 왜 중요할까?

- 읽기 전: IoT 산업은 계속 커지고 있고, 그만큼 실제 사고도 자주 일어난다. 최근에는 해커들이 프랑스의 혈장 보관용 냉동고를 장악해 온도 설정을 −30°C에서 110°C로 바꾼 일이 보도됐고([BBC 기사](https://www.bbc.com/news/articles/c8vgxyvz6y9ro)), 마트 냉장고에서도 비슷한 사고가 있었다([BBC 기사](https://www.bbc.com/news/articles/crq5nzxv9q4yo)). 이런 사례를 보면 해킹이 화면 속 데이터에서 끝나지 않고 현실의 물건과 사람에게까지 피해를 줄 수 있다는 것을 실감하게 된다.
- 읽은 후: high-order 취약점은 기존 도구로는 제대로 식별되지 않았을 뿐 아니라, 어떤 경로로 터지는지도 정확히 알 수 없었다. Bridge는 이 문제를 크게 개선했다.

### Q3. 기존 방법은 뭐가 부족했을까?

- 읽기 전: 보안 패치가 IoT 기기들에 신속히 적용되지 않아서 문제가 되지 않았을까?
- 읽은 후: 기존 taint 분석은 복잡한 IoT 기기에서 high-order 취약점을 분석하는 데 한계가 있었다. IoT 펌웨어는 여러 기능이 한데 묶인 일체형 구조라 분석이 어려웠고, 이를 해결하기 위해 이 논문은 Bridge라는 새로운 접근법을 제시한다.

## 배경과 문제 정의

### 이 문제가 생기는 환경

IoT 펌웨어는 일체형 구조라 요청을 처리하는 입구인 액션 진입 핸들러(AEH)가 바이너리 안에 숨어 있다. 또한 여러 요청이 공유하는 데이터에 대해, 어떤 요청이 어떤 코드를 실행시키는지(제어 의존성)가 분명하지 않다.

공유기를 예로 들면 요청은 아래 순서로 처리된다.

| 단계 | 누가 | 하는 일 | 예시 |
| --- | --- | --- | --- |
| 1 | 사용자(웹 UI) | 버튼을 누르면 액션 키워드가 담긴 HTTP 요청을 보낸다 | `SOAPACTION: SetNetwork` |
| 2 | 경계 바이너리 (요청을 가장 먼저 받는 프로그램) | 키워드를 보고 담당 핸들러(AEH)를 고른다 | `prog.cgi`, `httpd` |
| 3 | AEH (핸들러) | 값을 파싱해 NVRAM에 저장하거나, 다른 데몬에 실제 작업을 넘긴다 | `nvram_set`, 소켓, 시그널, `system()` |
| 4 | 백그라운드 데몬 | 넘겨받은 작업을 실제로 수행한다 | `rc` |

즉 하나의 기능이 여러 프로세스, 영구 저장소, 여러 요청에 걸쳐 구현된다.

### high-order 취약점이란

high-order 취약점이란 따로 보면 아무 문제가 없는 여러 요청이, 사용자가 조작할 수 있는 입력을 전달하면서 공격으로 이어지는 취약점이다. 일반적인 취약점들과 달리, 첫 요청이 넣은 오염된 데이터가 영구 저장소(NVRAM)에 보관돼 있다가 나중에 다른 요청이 그 값을 꺼내 쓸 때 터진다. 그래서 요청 하나만 봐서는 아무런 문제가 없어 보인다.

### 실제 사례: D-Link DIR882 (Figure 1)

Figure 1 사례에서 Request 1은 사용자가 조작할 수 있는 값을 NVRAM에 저장한다. 이후 Request 2가 다른 프로세스(rc)를 깨우고, rc가 NVRAM에서 그 값을 꺼내 `system()` 에 넘기면서 명령 주입 취약점으로 이어졌다.

단계별로 나눠 보면 아래와 같다.

1. **Request 1 (`SetNetwork`)**: `prog.cgi`의 핸들러가 사용자가 보낸 `DeviceName` 값을 `nvram_safe_set("lan0_management_link", v1)`으로 저장한다. (아무 일도 일어나지 않는다.)
2. **Request 2 (`SetVLAN`)**: 다른 핸들러가 `notify_rc("start_vlanall")`을 부르고, 이는 `sendto`로 127.0.0.1:6789에 메시지를 보낸다.
3. 데몬 `rc`가 `recvfrom`으로 메시지를 받아 `start_vlanall`이면 `vuln_func()`로 분기한다.
4. `vuln_func`는 `"lan" + "0" + "_management_link"`를 실행 중에 조립해 NVRAM에서 값을 읽고, `system("hostname %s")`에 그대로 넣는다. 명령 주입취약점으로 이어진다.

> 위 사례는 원문 논문의 Figure 1에 그려져 있다. ([원문 보기](https://doi.org/10.1109/SP63933.2026.00001))

### 기존 도구는 왜 이걸 못 잡았나

**① 숨겨진 통신 인터페이스와 프로세스 간 통신**

IoT 펌웨어는 프론트엔드와 백엔드가 주고받는 일이 많은데, 백엔드 인터페이스 상당수가 바이너리 안에 숨어 있어 직접 드러나지 않는다. 그래서 외부 입력을 놓치고 미탐이 생긴다. 또한 IoT 펌웨어에는 프로세스 사이의 데이터·제어 통신이 널리 쓰이는데, SUTURE 같은 리눅스 커널 대상 분석은 이를 고려하지 않아 역시 미탐으로 이어진다.

**② IPC 데이터 및 제어 의존성**

기존 IoT 펌웨어 정적 분석 도구는 키워드 매칭으로 IPC 데이터 의존성을 만들기 때문에, 실행 중에 만들어지는 키워드는 분석하지 못한다. 또 IPC 제어 의존성을 무시하기 때문에 경보만 울릴 뿐 실제로 어떤 경로로 터지는지는 보여 주지 못한다. 결국 동적 키워드와 제어 의존성을 무시하면 미탐이 생기고, 실제 취약점을 놓치게 된다.

**③ 동적 분석에서의 입력 공간 폭발**

동적 분석은 테스트 케이스를 실행해 보는 방식이라 모든 코드 경로를 커버하기 어렵다. high-order 취약점은 여러 요청의 실행 상태를 함께 추적해야 하므로 입력 공간이 크게 늘어난다. 결국 모든 경우를 탐색할 수 없어 취약점을 놓치고, 많은 미탐이 생긴다.

## 핵심 아이디어

### 해결 방향

펌웨어를 실행하지 않는 정적 분석으로 입력 공간 폭발 문제를 피한다. 그리고 데이터가 어디서 어디로 가는지(BDG)와 어떤 요청이 어떤 코드를 실행시키는지(ADG)를 각각 그래프로 만든 뒤 합쳐서, 여러 요청에 걸친 오염 흐름을 추적한다.

### 기존 도구와 결정적으로 다른 점

ADG를 도입함으로써, 기존 도구처럼 경보만 울리는 데서 그치지 않고 "어떤 요청을 어떤 순서로 보내면 터지는지"라는 실제 촉발 경로까지 보여 줄 수 있게 되었다.

## 방법론 / 시스템 설명

전체 흐름은 4단계다. 진입점 추출 → BDG 구성 → ADG 구성 → 취약점 분류. 진입점 추출의 결과가 두 갈래로 나뉘어, IPF는 데이터 쪽(BDG)의 시작점이, AEH는 제어 쪽(ADG)의 시작점이 된다. 두 그래프는 마지막 분류 단계에서 만난다.

```
① 진입점 추출
   │
   ├── IPF ──▶ ② BDG  (오염 데이터가 어디로 흐르는가)
   │
   └── AEH ──▶ ③ ADG  (어떤 요청이 어떤 코드를 실행하는가)

② + ③ ──▶ ④ 분류  (값을 저장한 요청 ≠ 꺼내 쓴 요청 → high-order)
```

> 전체 구조도는 원문 논문의 Figure 2를 참고하자. ([원문 보기](https://doi.org/10.1109/SP63933.2026.00001))

### 실제 사례(DIR882) 기반 전체 흐름(4단계) 설명

> Figure 1에 그려진 그림을 참조하며 작성했다. ([원문 보기](https://doi.org/10.1109/SP63933.2026.00001))

**1. 진입점 추출**

DIR882에서 AEH는 액션 키워드 `SetNetwork` 요청을 처리하는 핸들러와 `SetVLAN` 요청을 처리하는 핸들러이고, IPF는 사용자가 보낸 `DeviceName` 값을 꺼내는 함수(`webGetVarString`)이다. (Listing 2-1, 2-2의 `websFormDefine` 참조)
이 단계를 통해 바이너리 안에 숨은 핸들러와 입력 지점을 찾아 taint 분석의 출발점으로 삼는다.

**2. BDG 구성**

- OD-ICP: `vuln_func`는 키 이름을 `"lan" + "0" + "_management_link"`처럼 실행 중에 조립했다. 즉, `rc` 바이너리 안에는 `lan0_management_link`라는 문자열이 존재하지 않았고, 이 때문에 단순한 문자열 검색으로는 쓰는 쪽과 짝을 지을 수 없다. OD-ICP는 이걸 계산해서 `lan0_management_link`라는 키 이름을 복원한다. (Listing 2-3 `vuln_func()` 함수 참조)
- BDG 간선: `prog.cgi`의 `nvram_safe_set("lan0_management_link", v1)`(쓰기)와 `rc`의 `vuln_func` 안 `nvram_safe_get`(읽기)이 같은 키로 이어져, 데이터가 `prog.cgi`에서 NVRAM을 거쳐 `rc`의 `system()`까지 가는 길이 생긴다.

**3. ADG 구성**

- ADG 간선: `SetVLAN`이 `notify_rc`를 통해 `sendto`로 127.0.0.1:6789에 `start_vlanall` 메시지를 보내고, `rc`가 `recvfrom`으로 받아서 값이 `start_vlanall`이면 `vuln_func()`로 분기한다. (Listing 2-3 if/else문 참조)
- 이건 암묵적 제어다. `SetVLAN`이 `rc`를 직접 실행한 게 아니라 메시지만 보냈고, 어떤 코드가 실행될지는 받는 쪽(`rc`)이 메시지 값을 보고 정하기 때문이다.
- 반대로 명시적 제어는 `httpd`가 `system("sysctl -p 14")`로 `sysctl`을 직접 실행하는 것처럼, 누가 누구를 실행하는지가 코드에 바로 드러나는 경우다.

**4. 취약점 분류**

BDG와 ADG의 오염 정보를 따라가며 취약점을 찾는다. 여러 AEH가 함께 관여해야 터지면 high-order 취약점으로, 하나의 AEH와 하나의 요청만으로 터지면 일차 취약점으로 분류한다.
DIR882 사례에서 값을 쓴 요청은 `SetNetwork`, 꺼내 쓴 요청은 `SetVLAN`이다. 둘이 다르므로 high-order로 분류된다.

진입점 추출에서 Bridge가 찾는 AEH의 대표적인 코드 패턴은 세 가지다.

| 패턴 | 코드 모습 | 예시 벤더 |
| --- | --- | --- |
| 중첩 조건문 | `if (!strcmp(a3, "setEthPortLed")) ... else if ...` | Linksys |
| 등록 함수 | `websFormDefine("SetWanSettings", sub_465E68)` | D-Link |
| 함수 포인터 테이블 | `.data` 영역에 (문자열, 함수) 쌍이 나열됨 | Netgear |

### 이해하기 어려웠던 부분

전부 이해하기 어려워서 순서를 표시하며 읽었다. 순서를 따라가며 간략한 그림을 그려 이해했다. 그중에서도 BDG와 ADG 구성 단계가 가장 어려웠다.

그래서 나는 BDG는 "데이터가 어디로 가는지", ADG는 "누가 누구를 실행시키는지"로 구분해서 이해했다. BDG는 값을 쓰는 바이너리와 그 값을 읽는 바이너리를 짝지어, 데이터가 한쪽에서 다른 쪽으로 넘어가는 길을 이어 준다. ADG는 한 요청이 시그널, 프로세스 호출, IPC 메시지로 다른 프로세스를 깨워 코드를 실행시키는 관계를 보여 준다.

## 평가와 결과 해석

### 무엇과 비교했나

Bridge를 기존 도구인 Mango, SaTC와 비교했다. 실험에는 SaTC 데이터셋 12개(4개 제조사)와 저자들이 새로 모은 데이터셋 32개(8개 제조사), 총 44개의 실제 펌웨어를 사용했다.

### 가장 중요한 숫자와 그 의미

| 지표 | Bridge | Mango | SaTC |
| --- | --- | --- | --- |
| 정밀도 | 58.72% | 11.35% | 4.51% |
| 실제 취약점(TP) | 1,168 | 327 | 16 |
| high-order TP | 566 | 71 | 0 |
| 평균 분석 시간 | 3.06h | 8.86h | 63.23h |

- **정밀도**: 정밀도는 경보가 얼마나 정확한지를 뜻한다. Mango 대비 Bridge 경보가 진짜일 확률이 약 5배 높다. 찾아낸 실제 취약점 개수로 보면 1,168개 대 327개로 약 3.6배다.
- **high-order TP**: high-order 취약점은 Mango에 비해 8배 더 찾았고, SaTC는 한 개도 찾지 못했다. 이 논문이 풀려던 문제, 즉 여러 요청에 걸쳐 터지는 high-order 취약점 탐지를 실제로 풀었다는 것을 보여 주는 숫자다.
- **분석 시간**: 오히려 Bridge가 분석 시간도 더 빨랐다. 더 많고 정확하게 찾으면서도 시간은 오히려 줄었다는 점이 인상적이었다.

### 실제로 찾은 취약점

찾아낸 참양성을 제조사에 제보했고, 그중 90개가 0-day 취약점으로 확인되거나 CVE/PSV 번호를 받았다. 이 90개 중 45개가 high-order 취약점이다.

### RQ별 결과

> RQ(Research Question)는 실험으로 확인하려는 질문이다. TP(True Positive, 참양성)는 경보가 울렸고 실제로도 취약점이 맞았던 경우를 말한다.

**RQ1. high-order 취약점 탐지에서 Bridge는 얼마나 효과적인가?**

Bridge가 울린 경보 1,989개 중 실제 취약점(TP)은 1,168개였다. 이 중 566개가 high-order, 602개가 일차 취약점이었다. 분석 시간은 펌웨어 전처리부터 경보 생성까지 포함해 평균 3.06시간으로, Mango보다 2.9배, SaTC보다 20.7배 빨랐다.

**RQ2. 진입점 추출은 얼마나 효과적인가?**

펌웨어당 평균 48.53개의 숨겨진 AEH와 117.16개의 숨겨진 IPF를 식별했다. 정확도는 95.56%로 SaTC보다 높다.

**RQ3. BDG 구성은 얼마나 효과적인가?**

Bridge의 BDG는 평균 노드 수와 간선 수가 각각 SaTC BDG의 45배, 44배였다. 모든 펌웨어에서 Bridge의 BDG가 SaTC보다 더 완전했다. (부록 표 8)

**RQ4. ADG 구성은 얼마나 효과적인가?**

Bridge는 암묵적 IPC, 프로세스 호출, 시그널 제어 의존성에 대해 각각 509개, 2,346개, 677개의 TP를 식별했으며, 정밀도는 모두 84%를 넘는다.

## 한계점

### 논문이 스스로 밝힌 한계

논문에 적힌 한계들 중 일부는 아래와 같다. (인상 깊은거 3개만 추려보았다.)

1. **오탐의 원인은 taint 정제 처리 부족이다.**

   경보 1,989건 중 약 820건이 오탐.
   논문에서는 이 오탐이 모두 오염 전파 중 정제(sanitization) 처리가 부족해서 생겼다고 밝혔다. 
   펌웨어에 사용자 정의 함수가 많아 정제 함수를 다 설정하지 못하고, 그 결과 과잉 taint가 생겨 위와 같은 문제가 발생한다. 

2. **분석에 실패한 펌웨어가 있다.**

   Lua 기반 펌웨어는 분석하지 못했다. Tenda AX12는 IPC 함수가 사용자 정의 라이브러리 안에 깊이 감싸여 있어 taint 전파가 끊겼고, 취약점을 하나도 찾지 못했다. 이 문제는 Mango와 SaTC에서도 똑같이 나타났다. 


3. **적용 범위가 정해져 있다.**

   Bridge는 C/C++와 셸 스크립트로 된 웹 프론트엔드/백엔드 구조의 리눅스 펌웨어를 대상으로 한다. PHP·Lua 백엔드, 베어메탈·RTOS 펌웨어, 앱–클라우드–기기 구조는 다루지 않는다. 


### 내가 읽으며 느낀 아쉬운 점

- high-order 오염 분석을 하는 다른 방법(SUTURE 등)이 이미 있는 것 같은데, 관련 연구에서 언급만 하고 실험에서는 비교하지 않아 아쉬웠다.
- 사용자 입력을 파싱하는 부분을 모두 오염의 출발점으로 보는데, 처음에는 이게 무조건 오염으로 취급하는 것처럼 보여 비효율적이지 않나 싶었다. 나중에 알고 보니 입력을 오염의 출발점으로 보는 것은 오염 분석의 기본 전제였고, 진짜 문제는 그다음에 있었다. 입력이 검사·정제를 거쳐 안전해진 뒤에도 도구가 그 정제 함수를 알아보지 못하면 계속 오염으로 보고 경보를 울리고 이는 오탐으로 이어진다. (위에 적은 한계점 1번 참조)

## 느낀 점과 배운 점
처음에는 새로 발견된 IoT 취약점을 소개하는 논문인 줄 알았는데, 막상 읽어 보니 취약점을 찾는 분석 도구에 관한 논문이라 살짝 실망했다. 그런데 초록을 읽어보니 흥미가 생겼고, high-order 취약점처럼 처음 접하는 개념도 많이 접하게 되어, 어려웠지만 그만큼 배운게 많았다.

### 읽기 전과 후

- 읽기 전: IoT 사고가 일어나는 건 패치 속도가 취약점 발견 속도를 따라가지 못해서가 아닐까? AI 때문에 취약점이 더 빨리 발견되는 걸까? 최대한 빨리 패치하고, CVE가 올라오면 바로바로 확인해서 반영해야 하지 않나?
- 읽은 후: 애초에, 취약점이 어디서 터지는지조차 제대로 파악되지 않고 있었다. IoT 기기는 앞으로 더 늘어날 텐데 정말 큰일이다. Bridge가 제시되었지만 이것만으로는 아직 부족해 보인다. 여전히 미탐이 존재하기 때문이다. 

### 가장 인상 깊었던 개념: high-order 취약점

처음 알게 된 개념이고, 요청을 하나씩만 보면 안 보인다는 점이 신기했다. 각각은 평범한 설정 저장 요청과 실행 요청인데, 둘이 이어질 때만 공격이 된다는 점에서 이런 식으로도 공격이 가능하다는 것을 처음 배웠다.

### 읽다가 생각난 내 개인적인 경험

예전에 학습 목적으로 덤퍼저를 써서 바이너리를 분석해 본 적이 있다. 그때 코드 커버리지를 높이려고 대상 바이너리에 맞춰 퍼저를 손봤다. Bridge가 핸들러 진입점을 찾는 방식을 읽으며, "입력이 어디로 들어가는지 먼저 알아야 한다"는 고민이 내가 덤퍼저를 사용할 때와 유사해 반가웠다. (다만 내 퍼징은 직접 실행해 보는 동적 방식이고, Bridge는 실행하지 않고 코드에서 핸들러를 찾는 정적 방식이라는 점에서 차이가 있다.)

### 다른 분야에 적용한다면

Bridge는 결국 여러 요청과 여러 프로그램에 걸쳐 데이터가 어디로 가고 누가 무엇을 실행시키는지를 함께 분석해서 문제를 풀었다. 그렇다면 비슷한 구조를 가진 다른 분야에도 같은 방식을 적용할 수 있지 않을까?

high-order 방식의 취약점을 논문을 통해 공부하며 이전에 저장형 XSS 공격 기법에 대해 학습한 것이 떠올랐다. 공격자가 게시판에 악성 스크립트가 담긴 글을 쓰면, 그 글은 DB에 저장된다. 이 요청만 보면 그냥 글을 저장한 것뿐이다. 그런데 나중에 다른 사용자가 그 글을 열면 저장돼 있던 스크립트가 브라우저에서 실행된다. 이 요청도 혼자 보면 그냥 글을 읽은 것뿐이다. 두 요청이 이어져야만 공격이 된다는 점에서 Bridge가 다룬 high-order 취약점과 구조가 같다.

| | IoT 펌웨어 (Bridge) | 웹 애플리케이션 |
| --- | --- | --- |
| 값을 저장하는 요청 | `SetNetwork` | 글쓰기 |
| 저장소 | NVRAM | DB |
| 꺼내 쓰는 요청 | `SetVLAN` | 글 읽기 |
| 터지는 곳 | `system()` (명령 주입) | 브라우저 (스크립트 실행) |

실제로 논문의 관련 연구에서도 웹 애플리케이션의 high-order 취약점 연구를 소개하고 있다. 또 Bridge는 PHP 같은 웹 백엔드는 분석하지 못한다고 밝혔기 때문에(한계점 3번), Bridge의 "데이터 그래프 + 제어 그래프" 아이디어를 웹 쪽으로 적용해도 좋을 것 같다.


### 직접 해 보고 싶은 것

- Bridge가 공개한 코드와 데이터셋([Zenodo](https://doi.org/10.5281/zenodo.17232400))으로, 공개된 펌웨어 하나에 Bridge를 직접 돌려 보고 결과 경보를 하나씩 살펴보기

### 연구·프로젝트로 발전시킨다면

위에서 언급한대로, Bridge의 "데이터 그래프 + 제어 그래프" 아이디어를 웹 쪽으로 넓혀, 적용하는 프로젝트 혹은 연구를 진행하는 것도 좋은 프로젝트일 것 같다.
