## 논문 선정 이유

최근 확인한 여러 보안 뉴스들 중, IoT 관련 사고 뉴스를 접했었다. 논문 제목을 보고 IoT 관련 보안 논문인듯하여 큰 고민없이 바로 선정하고, 읽어 보았다.

> 한 줄 요약: 여러 요청에 걸쳐 터지는 high-order 취약점을 정적 분석으로 찾는 도구 **Bridge**를 제안했고, 펌웨어 44개에서 566개를 찾아 45개가 CVE/PSV로 확인됐다.

## 읽기 전, 스스로에게 던진 질문들

논문을 읽기 전, 제목만 보고 아래 질문들에 내 생각을 먼저 적어 두었다. 논문을 읽은 후에, 같은 질문에 대해 다시 답을 적어보았다.

**Q1. 이 논문이 다루는 문제는 무엇인가?**

- 읽기 전:
    - 리눅스 기반 IoT(사물인터넷) 기기의 취약점.
- 읽은 후:
    - 방향은 맞았지만 너무 넓었다. 이 논문의 정확한 타겟은 “**high-order taint 취약점**”이다(요청 한 번으로는 안 터지고 여러 요청이 순서대로 합쳐져야 터지는 취약점). 이걸 펌웨어를 실행하지 않고(정적 분석) 자동으로 찾는 것이 목표다.

**Q2. 왜 이 문제가 중요한가?**

- 읽기 전:
    - IoT 산업은 계속 커지고 있고, 그만큼 실제 사고도 자주 일어난다. 최근에는 해커들이 프랑스의 혈장 보관용 냉동고를 장악해 온도 설정을 −30°C에서 110°C로 바꾼 일이 보도됐고([BBC 기사](https://www.bbc.com/news/articles/c8vgxyvz6y9ro)), 마트 냉장고에서도 비슷한 사고가 있었다([BBC 기사](https://www.bbc.com/news/articles/crq5nzxv9q4yo)). 이런 사례를 보면 해킹이 화면 속 데이터에서 끝나지 않고 현실의 물건과 사람에게까지 피해를 줄 수 있다는 것을 실감하게 된다.
- 읽은 후:
    - 이번 냉동고 사례가 보여주듯 공격자가 노리는 것은 결국 기기의 **설정**이다. 이 논문의 high-order 취약점도 바로 설정을 저장하는 요청과 그 설정을 실행에 쓰는 요청이 따로 분리돼있어서 생긴다. 둘이 떨어져 있으니 도구도 사람도 놓치기 쉽다. 반면 공격자는 “설정 한 번 + 트리거 한 번”만으로 기기를 장악(원격 코드 실행)할 수 있다.

**Q3. 기존 방식들은 무엇이 부족했는가?**

- 읽기 전:
    - 잘 모르겠다. 보안 패치가 느리거나 부족한 것 아닐까?
- 읽은 후:
    - 여기서 말하는 “기존 방식”은 보안 패치가 아니라 **취약점을 찾는 분석 도구**(SaTC, Mango 등)였다. 이 도구들은 주로 요청 하나 단위로 분석했고, 프로그램 사이의 연결도 제한적으로만 다뤄서 아래 세 가지를 제대로 다루지 못했다.
        - ① 바이너리 안에 숨어 있는 요청 처리 입구(핸들러)를 찾지 못했다.
        - ② 저장소 키 이름이 실행 중에 조립되면, 값을 저장한 곳과 꺼내 쓰는 곳을 연결하지 못했다.
        - ③ 어떤 요청이 어떤 프로그램의 코드를 실행시키는지(제어 관계)를 고려하지 않았다.

## 이 논문이 등장한 배경과 문제의식

### 취약점이 “두 번에 나눠서” 터진다

이 논문의 출발점은 단순하다. IoT 펌웨어의 취약점은 이제 한 요청, 한 바이너리 안에서 끝나지 않는다는 것이다.

### IoT 기기는 어떻게 요청을 처리하나

공유기를 예로 들면 구조는 이렇다.

| 단계 | 누가 | 하는 일 | 예시 |
| --- | --- | --- | --- |
| 1 | 사용자(웹 UI) | 버튼을 누르면 액션 키워드가 담긴 HTTP 요청을 보낸다 | `SOAPACTION: SetNetwork` |
| 2 | **경계 바이너리** (요청을 가장 먼저 받는 프로그램) | 키워드를 보고 담당 핸들러(**AEH**, Action Entry Handler)를 고른다 | `prog.cgi`, `httpd` |
| 3 | AEH (핸들러) | 값을 파싱해 NVRAM에 저장하거나, 다른 데몬에 실제 작업을 넘긴다 | `nvram_set`, 소켓, 시그널, `system()` |
| 4 | 백그라운드 데몬 | 넘겨받은 작업을 실제로 수행한다 | `rc` |

즉 하나의 기능이 **여러 프로세스 + 영구 저장소 + 여러 요청**에 걸쳐 구현된다. 여기서 저자들이 주목한 것이 **high-order taint 취약점**이다. 요청 R1이 사용자 입력을 저장소에 쓰고, 나중의 요청 R2가 그 값을 읽어 위험 함수(sink)에 넘기는 구조다. 저장→읽기가 한 번 더 이어지면 3차, 4차가 된다.

### 실제 사례: D-Link DIR882의 0-day

논문이 동기 사례로 든 이 예시가 개념을 가장 잘 보여준다.

1. **Request 1 (`SetNetwork`)**: `prog.cgi`의 핸들러가 `DeviceName` 값을 받아 `nvram_safe_set("lan0_management_link", v1)`으로 저장한다. 여기까지는 아무 일도 안 일어난다.
2. **Request 2 (`SetVLAN`)**: 다른 핸들러가 `notify_rc("start_vlanall")`을 부르고, 이는 `sendto`로 127.0.0.1:6789에 메시지를 보낸다.
3. 데몬 `rc`가 `recvfrom`으로 메시지를 받아 `start_vlanall`이면 `vuln_func()`로 분기한다.
4. `vuln_func`는 `"lan" + "0" + "_management_link"`를 **런타임에 조립**해 NVRAM에서 값을 읽고, `system("hostname %s")`에 그대로 넣는다. 명령 주입이다.

> 두 요청과 두 프로세스 사이의 데이터·제어 흐름 전체는 원문 논문의 Figure 1에 그려져 있다. ([원문 보기](https://doi.org/10.1109/SP63933.2026.00001))

취약점이 터지려면 두 요청, 두 프로세스, 한 번의 NVRAM 저장, 한 번의 소켓 메시지가 모두 맞물려야 한다.

### 기존 도구의 한계점

저자들이 지적한 한계를 세 가지로 정리해 보았다.

| 한계 | 해당 도구 | 원인 | 결과 |
| --- | --- | --- | --- |
| **입구를 못 찾는다** | SaTC (USENIX Sec ’21) | 웹 화면(HTML/JS)에 나오는 문자열을 백엔드 바이너리에서 찾아, 일치하는 곳을 입력 지점으로 본다. 그런데 실제 요청 처리 함수는 함수 포인터 테이블이나 등록 함수를 거쳐 간접적으로 호출되는 경우가 많아 문자열만으로는 찾기 어렵다. 웹 화면 파일이 아예 없는 펌웨어(D-Link DCS932L)라면 비교할 문자열조차 없다. | 입력 지점을 제대로 추론하지 못한다 |
| **저장소를 거치면 추적이 끊긴다** | Karonte, SaTC | `nvram_set("고정문자열")`처럼 정적 키워드만 짝짓는다. 위 예시처럼 키워드를 실행 중에 조립하면 오염(taint) 전파가 거기서 끊긴다. | 저장소에 쓴 값을 다른 프로그램이 다시 읽는 지점까지 추적하지 못한다 |
| **요청과 실행 코드의 관계를 모른다** | Mango (USENIX Sec ’24) 등 | 사용자 입력이 위험 함수까지 흘러간다는 데이터 흐름은 알아내도, 어떤 요청이 어떤 데몬의 어떤 분기를 실행시키는지(제어 의존성)는 모델링하지 않는다. | 경보가 울려도 실제로 터뜨리는 요청 순서를 제시하지 못해, 사람이 다시 분석해야 한다 |

리눅스 커널 분야에는 SUTURE(CCS '21)처럼 high-order taint를 다룬 연구가 이미 있었다. 하지만 SUTURE는 시스템 콜과 전역 변수를 통해 값이 전달되는 경우를 다룬다. IoT 펌웨어처럼 NVRAM, 소켓, 시그널, 셸 스크립트로 프로그램끼리 값을 주고받는 환경에는 그대로 적용하기 어렵다. 퍼징 같은 동적 분석으로 찾으려 해도, 요청의 순서와 조합까지 모두 시도해야 해서 시도할 경우의 수가 너무 많아진다. Bridge는 바로 이 문제점들을 보완하기 위해 제안되었다.

## 저자들이 제안한 핵심 접근 방식

### 데이터 그래프와 제어 그래프를 따로 만들고 마지막에 합친다

**Bridge**의 핵심 아이디어는 다음 한 문장으로 요약된다. 

> **“오염 데이터가 어디로 흘렀는가(BDG)”와 “그 코드를 어떤 요청이 실행시키는가(ADG)”를 각각 펌웨어 전체 수준의 그래프로 만든 뒤, 쓰기와 읽기의 출발 요청이 다르면 high-order 취약점으로 분류한다.**

이 논문에서 '**high-order**'라는 모호한 개념을 **“쓰기 쪽 AEH ≠ 읽기 쪽 AEH”** 라는 기준으로 주로 판정해 간단하게 표현했다. (AEH가 같더라도 같은 요청을 두 번 보내야 터지는 경우는 high-order로 본다.)

전체 흐름은 **① 진입점 추출 → ② BDG 구성 / ③ ADG 구성 → ④ 취약점 분류**의 네 단계다. 진입점 추출의 결과가 두 갈래로 나뉘어, IPF는 데이터 쪽(BDG)의 시작점이, AEH는 제어 쪽(ADG)의 시작점이 된다. 두 그래프는 마지막 분류 단계에서만 만난다.

```
① 진입점 추출
   │
   ├── IPF ──▶ ② BDG  (오염 데이터가 어디로 흐르는가)
   │
   └── AEH ──▶ ③ ADG  (어떤 요청이 어떤 코드를 실행하는가)

② + ③ ──▶ ④ 분류  (값을 저장한 요청 ≠ 꺼내 쓴 요청 → high-order)
```

> 전체 구조도는 원문 논문의 Figure 2를 참고하자. ([원문 보기](https://doi.org/10.1109/SP63933.2026.00001))

### ① 진입점 추출: 패턴으로 후보를 뽑고, 키워드로 필터링

SaTC가 프론트엔드 키워드에서 출발해 백엔드를 찾았다면, **Bridge**는 반대로 백엔드 코드부터 본다. 요청 처리 함수(AEH)가 구현되는 대표적인 코드 패턴 세 가지를 먼저 찾는다.

| 패턴 | 코드 모습 | 예시 벤더 |
| --- | --- | --- |
| 중첩 조건문 | `if (!strcmp(a3, "setEthPortLed")) ... else if ...` | Linksys |
| 등록 함수 | `websFormDefine("SetWanSettings", sub_465E68)` | D-Link |
| 함수 포인터 테이블 | `.data` 영역에 (문자열, 함수) 쌍이 나열됨 | Netgear |

이렇게 찾은 키워드가 프론트엔드와 하나라도 겹치면 그 바이너리를 입구(**경계 바이너리**)로 확정하고, 그 안의 핸들러는 프론트엔드에 없더라도 모두 인정한다. 키워드는 "어느 바이너리가 입구인가"를 고르는 데만 쓰는 것이 핵심이다. 그 결과 펌웨어당 평균 48.5개의 숨은 핸들러를 추가로 찾았다. 사용자 입력을 꺼내는 함수(**IPF**, 예: `webGetVarString`)도 함수가 문자열 인자를 처리하는 방식을 분석하고 키워드 매칭을 활용해 찾아 오염 분석의 출발점으로 삼는다.

### ② BDG: 실행 중에 만들어지는 키 이름까지 복원한다

BDG는 오염된 값이 프로그램 사이를 어떻게 흘러가는지 그린 그래프다. 한 프로그램이 `nvram_set("키", 값)`으로 저장하면, 같은 키로 `nvram_get`을 부르는 다른 프로그램을 찾아 추적을 이어 간다.

문제는 키 이름이 `"lan" + "0" + "_management_link"`처럼 실행 중에 조립되는 경우다. Bridge는 **OD-ICP**(온디맨드 함수 간 상수 전파)로 이 문제를 푼다. 프로그램 전체가 아니라 키가 쓰이는 호출 지점에서만 거꾸로 값을 계산해, 조립된 키도 복원한다. 저자들이 표본을 검사했을 때 복원한 경로의 약 94%가 정확했다.

### ③ ADG: 어떤 요청이 어떤 코드를 실행시키는지 그린다

ADG는 요청이 프로그램 사이에서 어떻게 전달되는지 그린 그래프다. Bridge는 두 종류의 전달을 찾는다.

- **명시적 제어**: `system("sysctl -p 14")`처럼 다른 프로그램을 직접 실행하거나 시그널을 보내는 경우
- **암묵적 제어**: DIR882의 `start_vlanall`처럼 소켓 메시지를 보내면, 받는 쪽이 그 값을 보고 분기하는 경우

전달되는 값(`start_vlanall` 등)은 기호 실행으로 구한다. 프로세스 전체가 아니라 "이 값을 받으면 어느 분기가 실행되는가"까지 구분하는 것이 특징이다.

### ④ 분류: 값을 저장한 요청과 꺼내 쓴 요청을 비교한다

BDG에서 찾은 위험한 경로마다, 값을 저장한 요청과 꺼내 쓴 요청을 ADG로 거슬러 올라가 찾는다. 두 요청이 다르면 high-order 취약점이다. DIR882라면 저장은 `SetNetwork`, 사용은 `SetVLAN`이므로 high-order이고, 경보에 "`SetNetwork` → `SetVLAN`" 순서가 함께 기록된다. 그래서 결과가 단순한 경보가 아니라 "어떤 요청을 어떤 순서로 보내면 터지는가"까지 알려 준다.

> 각 단계의 세부 알고리즘(패턴 탐지 방법, OD-ICP 갱신 규칙, 기호 실행 최적화 등)은 원문 논문 3장과 부록 E를 참고하기 바란다.

## 실험 결과와 실제 성과, 혹은 드러난 한계

실험에는 8개 벤더(Netgear, D-Link, TOTOLink, Linksys, Tenda, ASUS, Motorola, Trendnet)의 실제 펌웨어 44개가 쓰였다. 기존 SaTC 데이터셋의 펌웨어 12개는 최신 버전으로 바꿔 사용했고, 저자들이 새로 모은 32개를 더했다. 비교 대상은 바이너리 간 오염 분석의 대표 도구인 Mango와 SaTC다. 도구가 낸 경보는 저자들이 실제 기기를 구입해 직접 디버깅하며 진짜 취약점인지 확인했다. 분석가 4명이 참여했고, 경보 하나를 확인하는 데 평균 15분이 걸렸다.

### RQ1. 취약점 탐지: 정밀도와 high-order 탐지에서 모두 앞섰다

| 도구 | 경보 | TP | 정밀도 | high-order TP | 펌웨어당 평균 시간 |
| --- | --- | --- | --- | --- | --- |
| **Bridge** | 1,989 | **1,168** | **58.72%** | **566** | **3.06h** |
| Mango | 2,882 | 327 | 11.35% | 71\* | 8.86h |
| SaTC | 355 | 16 | 4.51% | 0\* | 63.23h |

주: Mango·SaTC의 high-order 수치는 Bridge가 복원한 프로세스 간 제어 의존성을 저자들이 직접 제공한 뒤에 얻은 값이다.

**Bridge**는 진짜 취약점(TP)을 Mango보다 약 3.6배 많이 찾았다. 경보 중 진짜 취약점의 비율(정밀도)도 5배 넘게 높았다. 분석 속도는 Mango보다 2.9배, SaTC보다 20.7배 빨랐다.

실제 성과도 있었다. 90개의 새로운 취약점(0-day)이 제조사 확인을 받거나 CVE/PSV 번호를 받았고, 그중 45개가 high-order 취약점이다. 제조사가 단종(EoL) 기기라는 이유로 처리하지 않은 41개는 저자들이 VulDB와 MITRE에 직접 보고했다.

속도 차이는 분석 방향에서 나온다. Mango는 모든 바이너리의 모든 위험 함수에서 거꾸로 추적한다. 반면 **Bridge**는 요청이 들어오는 입구에서 출발해, 데이터와 제어가 실제로 닿는 바이너리만 따라가며 분석한다.

### RQ2–RQ4. 구성 요소별 기여

- **진입점 추출**: 경계 바이너리·AEH·IPF 식별 정밀도가 Bridge는 세 항목 모두 95.56%였다. SaTC는 각각 71.11%, 37.71%, 22.23%로 단계가 내려갈수록 떨어졌다(원문 Figure 5). 펌웨어당 평균 48.5개의 숨은 AEH와 117.2개의 숨은 IPF를 찾았다. 프론트엔드가 아예 없는 DCS932L에서도 `alphapd`를 입구로 잡아냈다.
- **BDG**: 평균 노드 808.5개, 간선 1,780개로 SaTC(18.2 / 40.9)의 45배, 44배다. 복원한 IPC 경로는 표본 기준 약 94%가 정확했다. 소거 실험에서는 IPF 식별과 OD-ICP를 각각 켜기만 해도 BDG가 커지고 취약점 수가 늘었다.
- **ADG**: 암묵적 IPC 509개, 프로세스 호출 2,346개, 시그널 677개의 제어 의존성을 모두 84% 이상의 정밀도로 찾았다. 유일한 비교 대상인 Chkup은 프로세스 호출 4개만 찾았다. high-order TP 566개 중 342개(약 60%)는 경계 바이너리 안에서 쓰고 읽는 경우였고, 나머지는 프로세스 호출 167개, 시그널 37개, 암묵적 IPC 20개가 관여했다.

### 한계점

저자들이 논문 5장(논의), 부록 A·E, 그리고 부록 F의 심사위원 메타 리뷰에서 밝힌 한계는 아래와 같다.

1. **오탐의 원인은 정제 처리 부족이다.**

   경보 1,989건 중 약 820건이 오탐이었고(논문 그림 4(a)에는 825건으로 표기), 저자들은 이 오탐이 모두 오염 전파 중 정제(sanitization) 처리가 부족해서 생겼다고 밝혔다. 펌웨어에 사용자 정의 함수가 많아 정제 함수를 다 설정하지 못하고, 그 결과 과잉 오염이 생긴다. 부록 E.1에서도 복잡한 별칭(aliasing)이나 불완전한 함수 요약 때문에 과잉 오염이 남을 수 있다고 인정한다. (4.2.1절, 부록 E.1)

2. **분석에 실패한 펌웨어가 있다.**

   Linksys MR7350은 Lua 기반이라 분석하지 못했다. Tenda AX12는 IPC 함수가 사용자 정의 라이브러리 안에 깊이 감싸여 있어 오염 전파가 끊겼고, 취약점을 하나도 찾지 못했다. 이 문제는 Mango와 SaTC에서도 똑같이 나타났다. 저자들은 데이터 흐름 분석과 LLM을 결합해 이런 래퍼 함수를 찾는 것을 향후 과제로 남겼다. (부록 A)

3. **과소 오염도 완전히 막지 못한다.**

   암묵적 흐름을 잡기 위한 2단계 전략이 많은 경우를 해결하지만, 오염된 분기의 결과가 여러 중간 계산을 거쳐 다른 제어 결정에 영향을 주는 다단계 암묵적 흐름은 여전히 놓칠 수 있다. 저자들은 이를 정적 오염 분석의 본질적인 트레이드오프로 보고, 더 발전된 포인터 분석과 경로 민감 기법이 필요하다고 했다. (부록 E.1)

4. **기호 실행은 일부 시간 초과로 끝난다.**

   경로 폭발을 막기 위해 탐색 범위를 줄이고 함수 요약과 5분 시간 제한을 두었지만, 실행의 약 10%는 여전히 시간 초과로 중단된다. 이것은 ADG의 완전성에 영향을 줄 수 있다. 또한 탐색 범위를 줄이는 가지치기 자체가 정적 분석의 정밀도에 크게 의존한다. (부록 E.2)

5. **적용 범위가 정해져 있다.**

   Bridge는 C/C++와 셸 스크립트로 된 웹 프론트엔드/백엔드 구조의 리눅스 펌웨어를 대상으로 한다. PHP·Lua 백엔드, 베어메탈·RTOS 펌웨어, 앱–클라우드–기기 구조는 다루지 않는다. 또 심볼 정보가 있는 동적 링크 바이너리를 전제로 하고, 복잡한 간접 호출은 해석하기 어렵다. (5장 논의)

6. **AEH 식별이 세 가지 코드 패턴에 의존한다.**

   심사위원 메타 리뷰에서 일반성을 제한하는 요소로 지적됐다. 저자들은 CVE 관련 펌웨어 200개 이상을 조사해 세 패턴으로 충분하다고 답했지만, 정적 패턴 매칭으로는 드문 사례를 놓칠 수 있다는 점은 인정했다. (부록 F·G)

7. **결과는 사람이 직접 검증해야 한다.**

   정적 분석 결과라 실제 기기를 사서 디버깅하며 확인했고, 이 과정에 숙련된 분석가 4명이 수백 시간을 들였다(경보당 평균 15분). 저자들은 정적 분석 결과의 자동 검증을 탐구할 가치가 있는 방향으로 꼽았다. (4.2.1절, 5장 논의)

#### 내가 느낀 아쉬운 점

- **얼마나 놓쳤는지는 알 수 없다.** 정답 데이터가 없어서, 미탐은 "Mango가 찾고 Bridge가 놓친 56건"처럼 다른 도구와 비교하는 방식으로만 분석했다. Bridge가 실제 취약점 중 몇 퍼센트를 찾았는지는 논문에서 정확히 알 수 없었다.

## 내가 느낀 점, 배운 점, 이후 해볼 만한 확장 아이디어

### 느낀 점과 배운 점

가장 크게 배운 점은 “**취약점을 어떤 단위로 보느냐**”가 **도구의 한계를 결정한다**는 것이다. 기존 도구들은 주로 요청 하나를 단위로 보며 프로그램 사이의 연결은 제한적으로만 다뤘고, **Bridge**는 “펌웨어 전체 + 요청의 순서”를 단위로 보았다. 그 관점 전환을 BDG(데이터)와 ADG(제어)라는 두 그래프로 구체화했기 때문에, 결과물이 경보 목록이 아니라 “어떤 요청을 어떤 순서로 보내면 터지는가”라는 재현 경로가 되었다.

두 번째는 **모든 걸 정밀하게 하지 않아도 된다는 것**이다. OD-ICP는 필요한 호출 지점에서만 상수를 풀고, 기호 실행은 제어 값을 만드는 블록에만 돌리며, 무관한 함수는 제약 없는 기호 값으로 건너뛴다. 정적 분석에서 정밀도와 확장성의 균형을 어디에 두는지를 구체적으로 보여주는 설계였다.

세 번째는 **취약점을 찾는 것만큼 확인하는 일도 크다는 것**이다. 저자들은 분석가 4명이 실제 기기를 사서 경보를 하나하나 디버깅했고, 경보 하나에 평균 15분이 걸렸다. 이런 도구의 가치는 결국 “사람이 직접 확인해야 하는 경보가 얼마나 적은가”로 평가된다는 것을 느꼈다.

논문을 읽기 전에는 기존 방식의 한계가 "보안 패치가 느리다"는 데 있다고 생각했다. 하지만 실제 문제는 패치가 아니라 분석 도구 쪽에 있었다. 기존 도구들은 바이너리 안에 숨은 요청 처리 입구를 찾지 못했고, 여러 요청이 어떻게 이어지는지도 보지 못했다.

### 이 논문을 바탕으로 더 읽어볼 논문

| 논문 | 학회 | 읽는 이유 |
| --- | --- | --- |
| Sharing More and Checking Less: Leveraging Common Input Keywords to Detect Bugs in Embedded Systems (SaTC; Chen et al.) | USENIX Security 2021 | Bridge가 출발점으로 삼은 연구. 프론트엔드와 백엔드가 공유하는 키워드로 입력 지점을 찾는다. Bridge를 읽은 뒤에 보면 무엇이 개선됐는지 더 잘 보인다. |
| Operation Mango: Scalable Discovery of Taint-Style Vulnerabilities in Binary Firmware Services (Gibbs et al.) | USENIX Security 2024 | Bridge의 주 비교 대상. 같은 문제를 다른 방식(싱크에서 거꾸로 추적)으로 푼 연구라 두 논문을 비교하며 읽기 좋다. |

### 비슷한 문제를 다른 분야에 적용한다면

“**쓰는 요청과 읽는 요청이 다르고, 그 사이에 저장소와 IPC가 있다**”는 구조는 IoT만의 것이 아니다.

- **차량 인포테인먼트/AUTOSAR Adaptive**: SOME/IP·D-Bus 서비스가 설정값을 저장하고 다른 서비스가 읽는다. 메시지 ID를 제어 값으로 보면 ADG와 비슷한 분석을 적용해 볼 수 있을 것 같다.
- **안드로이드 시스템 서비스**: Binder 트랜잭션 코드가 액션 키워드, `setprop`/`getprop`이 NVRAM 역할을 한다. 설정 앱에서 저장한 값이 네이티브 데몬의 `system()`에 닿는 경로를 찾는 데 응용해 볼 수 있을 것이다.
- **산업용 게이트웨이·리눅스 기반 PLC 런타임**: 논문의 참고문헌에도 있듯 Moxa 장비에서 2차 명령 주입(CVE-2023-33239)이 이미 나왔다.
- **마이크로서비스 백엔드**: Redis·메시지 큐가 영구 저장소, 큐 토픽이 페어링 키워드가 된다. 웹 분야의 2차 SQLi 탐지를 서비스 간 수준으로 넓혀 볼 수 있을 것이다.

### 직접 해 보고 싶은 것

- 제조사 홈페이지에서 공개된 공유기 펌웨어 하나를 받아 Binwalk로 파일 시스템을 풀어 보고, `httpd`나 `.cgi` 같은 웹 처리 바이너리가 어디 있는지 찾아보기
- 그 바이너리를 열어 논문에 나온 세 가지 AEH 패턴(`strcmp` 연쇄, 등록 함수, 함수 포인터 테이블) 중 어떤 것이 쓰였는지 눈으로 확인하기
- 같은 펌웨어에서 `nvram_set`/`nvram_get`(또는 비슷한 함수) 호출을 검색해, 어떤 키를 어느 바이너리가 쓰고 읽는지 표로 정리해 보기
- 공개된 Bridge 아티팩트(Zenodo)의 README와 코드 구조를 읽고, 논문의 ①~④ 단계가 코드에서 어디에 해당하는지 짝지어 보기
- 논문 표 2에서 펌웨어별로 Bridge·Mango·SaTC의 경보 수와 TP를 나란히 놓고, 세 도구의 차이가 특히 큰 펌웨어를 골라 그 이유를 논문에서 찾아보기

### 연구·프로젝트로 발전시킨다면

아직은 공부가 먼저라고 생각해서, 작은 프로젝트로 이어 가는 순서로 계획을 세웠다.

1. **개념 공부**: 오염 분석(taint analysis: 소스·싱크·전파), CFG·호출 그래프, 리눅스 IPC(NVRAM, 소켓, 시그널)를 하나씩 정리한다.
2. **바이너리 분석 도구에 익숙해지기**: Binwalk, IDA, Ghidra로 실제 펌웨어를 열어 보며 논문에 나온 구조를 직접 확인한다.
3. **작은 실습으로 이어가기**: 위에서 만든 “키를 쓰는 곳 / 읽는 곳” 표를 간단한 Python 스크립트로 자동화해 보고, 키 이름이 문자열 조립으로 만들어지는 경우 단순 검색이 왜 놓치는지 직접 체감해 본다. 이것이 논문에서 OD-ICP가 필요했던 이유를 이해하는 가장 쉬운 길이라고 생각한다.

이 과정을 거친 뒤에 SaTC, Mango 같은 도구를 직접 돌려 보며 조금씩 따라가 보고 싶다.
