### 0-2. A04:2025 - Cryptographic Failures

**Cryptographic Failures(암호 체계 실패)** 는 웹 애플리케이션에서 민감한 데이터를 보호하기 위해 사용되는 암호학적 보안 기능이 제대로 적용되지 않거나, 잘못 구현·관리되어 데이터가 노출되는 보안 위험을 의미한다.

암호화가 적용되지 않은 채 데이터가 전송되거나 저장되는 경우, 취약한 암호 알고리즘을 사용하거나 암호키를 부적절하게 관리하는 경우 등이 이에 해당한다. 이러한 문제는 개인정보, 비밀번호, 결제 정보 등 민감한 데이터의 노출로 이어질 수 있다.

OWASP는 이러한 문제를 방지하기 위해 민감한 데이터의 식별과 보호, 검증된 암호 알고리즘의 사용, 안전한 암호키 관리, 안전한 통신 환경 구축 등을 권장하고 있다.

최근 Cryptohack 사이트를 활용해 암호학 공부를 시작했고, 마침 OWASP Top 10에도 암호학 관련 주제가 있어 해당 주제에 관해 학습하고, 글을 정리해 보았다.

## 1. 암호학적 실패(Cryptographic Failures)란?

### 1-1. 암호학적 실패의 정의

**암호학적 실패**란 민감한 데이터를 보호하기 위한 암호학적 보안 기능이 적용되지 않았거나, 잘못 구현 또는 관리되어 데이터가 노출되거나 보호 기능이 제대로 동작하지 않는 보안 문제를 의미한다.

예를 들어, 개인정보를 암호화하지 않은 채 저장하거나, 암호 알고리즘이 취약한걸 사용하거나하는 경우 등이 이에 해당한다.

암호학적 실패는 단순히 암호화가 적용되지 않은 경우만을 의미하는 것은 아니다. 암호학적으로 안전한 알고리즘을 사용하더라도 알고리즘을 잘못 적용하거나 암호키를 부적절하게 관리하면 보안 문제가 발생할 수 있고 이도 암호학적 실패에 포함된다.

즉, 암호학적 실패는 암호화 기술 자체의 문제뿐 아니라 암호학적 기술을 사용하는 과정에서 발생하는 여러 실수까지 포함한다.

### 1-2. 암호학의 4요소

암호학은 데이터를 보호하기 위해 다양한 기술을 활용한다. 

- 기밀성(Confidentiality)
- 무결성(Integrity)
- 인증(Authentication)
- 부인방지(Non-repudiation)

**1) 기밀성(Confidentiality)**   
**기밀성**이란 허가된 사용자만 데이터의 내용을 확인할 수 있도록 보호하는 것을 의미한다.   
데이터를 암호화하면 암호키를 가지고 있지 않은 사람은 암호화된 데이터를 읽기 어렵게 만들 수 있다. 이를 통해 개인정보, 비밀번호, 금융 정보 등 민감한 데이터가 권한 없는 사람에게 노출되는 것을 방지할 수 있다.   

**2) 무결성(Integrity)**   
**무결성**이란 데이터가 허가되지 않은 방식으로 변경되지 않았음을 확인할 수 있도록 하는 것을 의미한다.   
데이터가 전송되거나 저장되는 과정에서 누군가 내용을 변경했다면, 이를 탐지할 수 있어야 한다. 암호학에서는 해시(Hash), 메시지 인증 코드(MAC), 디지털 서명 등의 기술을 활용하여 데이터의 변조 여부를 확인할 수 있다.   
다만, 일반적인 해시값만으로는 공격자가 데이터와 해시값을 모두 변경하는 상황을 방지할 수 없다. 따라서 공격자의 변조를 탐지하기 위해서는 MAC이나 디지털 서명 등 적절한 인증 수단이 필요한 경우가 있다.   

> 중세 시대를 배경으로 한 영화에서 편지를 보낼 때 촛농을 떨어뜨리고 가문의 인장을 찍는 장면을 종종 볼 수 있다. 편지를 열면 봉인이 훼손된 흔적이 남고, 인장은 위조하기 어려워 편지가 전달되는 동안 개봉되었는지 확인하는 데 도움이 된다. 이처럼 인장은 무결성을 확인하는 역할을 한다.
> 

**3) 인증(Authentication)**   
**인증**이란 통신 상대방이나 데이터의 출처가 신뢰할 수 있는 대상인지 확인하는 것을 의미한다.   
웹사이트에 접속할 때 서버 인증서를 검증하면 사용자가 접속한 서버가 해당 도메인에 대해 신뢰할 수 있는 인증서를 제시했는지 확인할 수 있다. 또한 디지털 서명을 통해 메시지가 특정 서명자의 개인키로 서명되었는지 검증할 수 있다.   
이러한 인증 과정은 공격자가 정상적인 서버나 사용자로 위장하는 것을 방지하는 데 도움을 준다.   

**4) 부인방지(Non-repudiation)**   
**부인방지**란 송신자나 수신자가 메시지 송·수신 또는 서명 행위를 나중에 부인할 수 없도록 암호학적 증거를 제공하는 것을 의미한다.   
일반적인 MAC이나 대칭키 방식에서는 키를 공유하는 양측 모두 메시지를 생성할 수 있으므로, 누가 보냈는지 제3자에게 입증하기 어렵다. 반면 비대칭키 기반의 디지털 서명을 사용하면 서명자의 개인키로 생성된 서명임을 검증할 수 있어, 송신자가 전송·서명 사실을 부인하는 것을 막는 근거가 된다.

## 2. 암호학적 실패 유형

암호학적 실패는 다양한 원인으로 발생할 수 있다. 대표적으로 다음과 같은 경우를 살펴볼 수 있다.

- **민감한 데이터의 암호화 누락**: 개인정보, 비밀번호, 금융 정보 등 보호해야 할 데이터를 평문으로 저장하거나 전송하는 경우.
- **취약하거나 오래된 암호 알고리즘 사용**: 보안성이 충분하지 않은 알고리즘이나 암호화 방식을 사용하여 데이터 보호가 제대로 이루어지지 않는 경우.
- **비밀번호 저장 방식의 문제**: 비밀번호를 평문으로 저장하거나, 비밀번호 보호에 적합하지 않은 빠른 해시 함수만 사용하는 경우.
- **암호키 관리 실패**: 암호키를 소스코드에 하드코딩하거나, 암호키가 외부에 노출되거나, 부적절하게 관리되는 경우.
- **안전하지 않은 난수 생성**: 보안에 필요한 키나 토큰 등을 예측 가능한 난수로 생성하는 경우.

### 2-1. 민감한 데이터의 암호화 누락

웹 애플리케이션은 사용자 개인정보, 로그인 정보, 결제 정보 등 다양한 중요 데이터를 처리한다. 이러한 데이터가 적절히 보호되지 않는다면 유출 시 사용자와 서비스 모두에게 큰 피해가 발생할 수 있다.
중요한 데이터는 저장되어 있을 때 뿐만 아니라 다른 시스템으로 전송되는 과정에서도 보호되어야 한다.
(예를 들어, 사용자가 웹사이트에 로그인할 때 아이디와 비밀번호가 암호화되지 않은 상태로 네트워크를 통해 전송된다면, 공격자가 네트워크 통신을 관찰할 수 있는 환경에서 해당 정보를 탈취할 가능성이 있다.)
또한 데이터베이스에 개인정보를 평문으로 저장하는 경우 데이터베이스가 유출되었을 때 공격자는 별도의 복호화 과정 없이 데이터를 확인할 수 있다.
따라서 애플리케이션은 보호해야 할 데이터를 식별하고, 데이터가 저장되거나 전송되는 환경에 적절한 보호 조치를 적용해야 한다.

### 2-2. 취약하거나 오래된 암호 알고리즘 사용

암호 알고리즘은 데이터를 보호하기 위해 사용되는 수학적 방법이다. 이런 모든 암호 알고리즘이 동일한 수준의 보안성을 갖고 있지는 않다.
과거에는 안전하다고 여겨졌던 알고리즘도 컴퓨팅 기술의 발전이나 새로운 공격 기법의 발견으로 더 이상 안전하지 않다고 평가될 수 있다.
대표적으로 MD5와 SHA-1은 충돌 공격에 대한 취약점이 알려져 있어 새로운 보안 시스템에서 사용이 권장되지 않는다. 또한 AES를 사용하더라도 ECB와 같은 부적절한 암호화 모드를 사용하면 데이터의 패턴이 노출될 수 있다.
즉, 암호 알고리즘을 선택할 때는 단순히 암호화 기능이 제공되는지를 확인하는 것이 아니라, 현재 보안 기준에 적합한 것을 선택하는 것이 중요하다.

### 2-3. 비밀번호를 안전하지 않게 저장

사용자가 웹사이트에 가입할 때 입력한 비밀번호는 인증을 위해 데이터베이스에 저장되는 경우가 많다. 이때 비밀번호를 그대로 평문 상태로 저장하면 데이터베이스가 유출되는 순간 사용자의 비밀번호가 그대로 노출될 수 있다.

그렇다면 비밀번호를 어떻게 저장할까?

비밀번호를 굳이 암호화 시켜도 비밀번호는 로그인 과정에서 원래 비밀번호를 복호화할 필요가 없다. 사용자가 입력한 비밀번호와 저장된 값을 비교하여 인증 여부만 판단하면 되기 때문이다. (일반적인 암호화는 암호키를 사용하여 원래 데이터를 복구할 수 있는 방식이다.)
따라서 비밀번호 저장에는 일반적인 암호화보다 비밀번호 전용 **해시 함수**가 적합하다.

> **해시(Hash)**
해시 함수는 입력 데이터의 크기와 관계없이 일정한 길이의 해시값을 생성하는 함수이다.
> 
> 
> 예를 들어, 어떤 문자열을 SHA-256으로 처리하면 256비트 길이의 해시값이 생성된다. 입력값이 조금만 달라져도 결과 해시값은 크게 달라질 수 있다.
> 
> 해시 함수는 일반적으로 원래 입력값을 해시값으로부터 역으로 복구하기 어렵도록 설계되어 있다. 이러한 특성을 활용하여 데이터의 무결성 확인이나 비밀번호 저장 등에 사용한다.
> 
> 그러나 SHA-256과 같은 일반적인 해시 함수는 계산 속도가 매우 빠르다는 특징이 있다. 공격자가 유출된 해시값을 획득하면 다양한 비밀번호 후보를 빠르게 계산하여 비교할 수 있다.
> 

> **Salt**
> 
> 
> Salt는 비밀번호를 해시할 때 함께 사용하는 무작위 값이다.
> 
> 같은 비밀번호를 사용하는 여러 사용자가 있더라도 서로 다른 Salt를 적용하면 일반적으로 서로 다른 해시값이 생성된다. 이를 통해 동일한 비밀번호가 저장되어 있는지 쉽게 확인하기 어렵게 만들고, 사전에 계산된 해시값을 활용하는 레인보우 테이블 공격의 효율을 크게 떨어뜨릴 수 있다.
> 
> 하지만 Salt를 적용하는 것만으로 비밀번호가 완전히 안전해지는 것은 아니다. 공격자는 개별 해시에 대해 비밀번호 후보를 계속 계산할 수 있기 때문이다.
> 
> 따라서 비밀번호 저장에는 Argon2id, bcrypt, scrypt, PBKDF2와 같이 비밀번호 저장에 적합한 알고리즘을 사용하고, 개별 Salt와 적절한 계산 비용을 설정하는 것이 중요하다.
> 

### 2-4. 암호키 관리 실패

암호키는 암호화와 복호화에 사용되는 중요한 정보이다. 안전한 암호 알고리즘을 사용하더라도 암호키가 공격자에게 노출되면 해당 키로 보호되는 데이터의 보안성이 크게 떨어질 수 있다.

예를 들어, 개발자가 암호키를 소스코드에 직접 작성하는 경우 소스코드가 외부에 공개되거나 유출되었을 때 공격자가 암호키를 획득할 수 있다.

또한 암호키를 여러 시스템에서 무분별하게 재사용하거나, 접근 권한을 적절히 관리하지 않거나, 키가 노출되었는데도 교체하지 않는 경우 문제가 발생할 수 있다.

암호키는 암호화된 데이터만큼 중요하게 보호해야 하며, 키 생성, 저장, 접근 제어, 교체, 폐기 등의 관리 과정이 필요하다.

### 2-5. 안전하지 않은 난수 생성

암호학에서는 암호키, 세션 토큰, 인증 토큰, 초기화 벡터 등 다양한 값을 생성할 때 난수가 사용된다.

일반적인 프로그램에서도 난수를 생성할 수 있지만, 모든 난수 생성 방식이 보안에 적합한 것은 아니다.

예를 들어, 일반적인 난수 생성 함수는 게임이나 시뮬레이션 등의 용도로 설계되어 있을 수 있다. 대표적으로 C 언어의 `rand()` 같은 함수는 완전한 무작위 값을 만들어내는 것이 아니라, 초기 시드(seed) 값에 정해진 수학적 규칙을 적용해 순서대로 값을 계산하는 방식(의사난수 생성기, PRNG)을 사용한다. 겉보기에는 무작위처럼 보여도 생성 규칙이나 시드 값이 노출·추측되면 다음 난수 역시 예측할 수 있으므로 보안 목적에는 적합하지 않다.

만약 공격자가 생성된 난수를 예측할 수 있다면, 해당 난수를 기반으로 만들어진 토큰이나 키를 추측할 가능성이 생긴다.
따라서 보안 목적의 난수를 생성할 때는 암호학적으로 안전한 난수 생성기(CSPRNG)를 사용해야 한다.

> | **구분** | **일반 PRNG** | **CSPRNG** |

## 4. 암호학적 실패를 방지하는 방법

암호학적 실패를 방지하기 위해서는 단순히 암호화 기능을 적용하는 것만으로 충분하지 않다. 어떤 데이터를 보호해야 하는지 식별하고, 적절한 암호학적 기술을 선택하며, 이를 안전하게 구현하고 관리하는 과정이 필요하다.

### 4-1. 민감한 데이터 식별 및 보호

애플리케이션에서 처리하는 모든 데이터를 동일한 수준으로 보호할 필요는 없다. 먼저 어떤 데이터가 민감한 데이터인지 식별하고, 해당 데이터가 저장되거나 전송되는 과정에서 적절한 보호 조치를 적용해야 한다.

예를 들어, 개인정보, 인증 정보, 금융 정보, 사업상 기밀 정보 등은 유출될 경우 피해가 발생할 수 있으므로 적절한 보호가 필요하다.

또한 굳이 저장 안해도 되는 중요한 데이터는 가급적 저장하지 않는 것이 좋다. 당연한 말이겠지만 데이터가 저장되지 않는다면 해당 데이터가 유출될 위험도 없어진다.

### 4-2. 검증된 암호 라이브러리와 알고리즘 사용

암호학은 수학적으로 복잡하고 구현 과정에서 작은 실수도 보안 문제로 이어질 수 있다.

따라서 직접 암호 알고리즘을 구현하기보다는 신뢰할 수 있고 검증된 암호 라이브러리를 사용하는 것이 좋다.

또한 MD5, SHA-1 등 현재 사용이 권장되지 않는 알고리즘이나 안전하지 않은 암호화 설정을 피하고, 최신 보안 기준에 맞는 알고리즘과 설정을 선택해야 한다.

암호화 기능을 구현할 때는 알고리즘의 이름만 확인하는 것이 아니라, 암호화 모드, IV 또는 nonce 사용 방식, 인증 기능 등도 함께 고려해야 한다.

### 4-3. 비밀번호는 암호화가 아닌 안전한 해시 방식으로 저장

비밀번호는 복호화할 필요가 없는 데이터이므로 일반적인 암호화 방식으로 저장하기보다 비밀번호 전용 해시 함수를 사용하는 것이 적절하다.

Argon2id, bcrypt, scrypt, PBKDF2 등의 알고리즘은 비밀번호 저장을 위해 활용할 수 있다.

또한 각 비밀번호에 고유한 Salt를 적용하고 적절한 계산 비용을 설정하여 공격자가 비밀번호를 추측하는 데 더 많은 자원을 사용하도록 해야 한다.

비밀번호 저장 방식은 시스템의 보안성을 결정하는 중요한 요소이므로, 검증된 라이브러리와 권장 설정을 활용하는 것이 좋다.

### 4-4. 암호키의 안전한 관리

암호키는 암호화된 데이터를 보호하는 핵심 요소이므로 안전하게 관리해야 한다.
암호키를 소스코드에 직접 작성하지 않고 별도의 안전한 저장소에 보관하며, 암호키에 접근할 수 있는 사용자와 시스템을 제한해야 한다.
또한 암호키가 노출되었을 때 이를 교체할 수 있도록 키 교체 정책을 마련하고, 암호키가 더 이상 필요하지 않은 경우 안전하게 폐기하는 절차도 필요하다.

### 4-5. 안전한 통신 환경 구축

웹 애플리케이션에서 데이터를 전송할 때는 TLS를 활용하여 통신을 보호해야 한다.
HTTPS는 TLS를 기반으로 통신 내용을 암호화하고 데이터의 무결성을 보호하며, 서버 인증을 통해 사용자가 신뢰할 수 있는 서버와 통신하도록 돕는다.
또한 웹사이트 전체에 HTTPS를 적용하고, 안전하지 않은 TLS 설정을 사용하지 않도록 관리해야 한다.
HSTS를 적용하면 브라우저가 해당 사이트에 HTTPS로만 접속하도록 강제하는 데 도움이 된다.

## 5. 마무리

### 5-1. 학습하며 느낀 점

이번에 OWASP Top 10의 A04:2025 Cryptographic Failures를 공부하면서 암호학적 실패가 단순히 암호 알고리즘 문제만 다루는 것이 아니라, 기술을 적용하고 관리하는 과정에서 발생하는 다양한 문제를 포함한다는 것을 알게 되었다.

암호화 알고리즘의 보안 수준이 아무리 뛰어나도, 결국 이를 적용하는 것은 사람이고 그렇기에 실수가 있을 것이고 그 실수들이 큰 취약점이 된다는걸 배우며, 결국 리얼월드에서는 알고리즘을 기술적으로 분석해, 뚫는것보다 이런 실수들을 찾아내는 것이 훨씬 더 치명적이고, 실용적일 것 같단 생각이 들었다.

### 5-2. Cryptohack 학습과 연결해서 앞으로 공부할 것

최근 Cryptohack을 통해 암호학 공부를 시작하면서 다양한 암호학 알고리즘과 다양한 문제를 접하고 있다.앞으로 Cryptohack을 통해  암호학의 기본 개념을 더 공부하고, 이러한 개념들이 실제 웹 보안 취약점과 어떻게 연결되는지 알아보고 싶다.
